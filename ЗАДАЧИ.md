### Отклонено по итогам ревью (осознанно)

- **Потоковый экспорт/импорт ZIP** — бэкап содержит только `.local/share/opencode`,
  `.config/opencode`, `.gitconfig`, `.ssh` (`SettingsActivity.java:384`), а не
  рабочие проекты. 512 МБ / 20 000 файлов там с запасом.
- **Стриминг загрузки >128 МБ** — польза сомнительна (провайдеры моделей всё
  равно режут вложения), а правка самая дорогая. При необходимости поднимем
  лимит, а не перепишем парсер.
- **Авторизация в `ProxyServer`** — риск сломать `git`/`pip`/`bun`, выигрыш
  мизерный (прокси только на `127.0.0.1`).
- **CSP** — страница на инлайн-скриптах: без `unsafe-inline` не работает, с ним
  бесполезен.
- **Рефакторинг декомпилированного Java** — риск без тестов выше пользы.
- **`killOrphans` через `ps`** — почти пустая операция, но и не мешает;
  реальную защиту даёт pid-файл.
- **`/sdcard/p`** — там только uid и домашний путь; достаточно описать в доке.

### Осознанно не делаем

- Не убираем `debuggable` и CDP — на них держится отладка (`run-as`,
  `adb push` страницы, `tools/cdp.py`).
- Не ставим короткие таймауты на shell-команды — это отнимет у агента
  длинные операции.
- Не запрещаем обновления OpenCode новее «проверенной» версии.
- Не трогаем `setMixedContentMode` — для http-страницы это ни на что не влияет.

## Задача 3. Уведомления — только по завершении полного ответа (✅ сделано 2026-11-08)

### Результат

- `Notifications.show()` проверяет преф `notify` и использует **фиксированный
  ID 1001** — новое уведомление заменяет старое, а не плодит записи.
- `RuntimeService.notifyLoop()` больше не показывает уведомление на каждый
  `session.execution.succeeded/failed/interrupted`. Вместо этого
  `scheduleCheck()` ставит отложенную проверку на 1.8 с, а `checkDone()`
  опрашивает `GET /api/session/{id}` и показывает уведомление только если
  `time.idle >= time.busy` (сессия реально свободна). Если ещё занята — до
  5 повторов по 1.5 с. Новое событие `started` отменяет отложенное.
  Состояние: `pendingStamp` (метка на сессию), `pendingType`, `askedIds`.
- `permission.asked` / `form.created` дедуплицируются по `id` запроса
  (`askedIds`) и уважают `notify`.
- Из `page.html` убраны дубли `BR.notify` (запрос разрешения и переход
  `busy → idle`) — уведомляет только нативный watcher; на странице остались
  вибрация/тост.
- Проверено на телефоне (`deepseek-v4.1-flash`, ответ с 4 инструментами):
  - галочка вкл → **ровно одно** новое уведомление `id=1001`
    («OpenCode / Ответ готов»), без дублей;
  - галочка выкл → новых записей нет, `when` не изменился.

### Что было не так

Сейчас уведомления приходят несколько раз за один ответ: во время
«раздумий», вызовов инструментов и промежуточных шагов. Должно быть **одно
уведомление**, когда ответ полностью готов, и только если включена галочка
«Уведомления о завершении».

### Причины (точки в коде)

- `RuntimeService.notifyLoop()` (~строка 280): на каждое событие
  `session.execution.succeeded/failed/interrupted` показывает «Ответ готов».
  Один ответ может содержать несколько execution (шаги/инструменты) — отсюда
  несколько уведомлений.
- `Notifications.show()` (~18): не проверяет преф `notify`, поэтому галочка
  в настройках ни на что не влияет.
- `page.html`, `handle()` (~1513): при переходе `busy → idle` тоже вызывает
  `BR.notify(...)`, не глядя на настройку — возможен дубль с нативным
  watcher.

### Что сделать

1. `Notifications.show()`: в начале
   `if (!App.prefs().getBoolean("notify", true)) return;`
   (отдельно решить, что делают `sound`/`vib`).
2. `RuntimeService.notifyLoop()`: вместо немедленного уведомления на каждый
   `succeeded` — отложенное (debounce ~1.5–2 с) на сессию:
   - на `session.execution.started` — отменить отложенное уведомление и
     добавить сессию в `active`;
   - на `succeeded/failed/interrupted` — запомнить «последнее завершение»;
   - через 1.5–2 с проверить `GET /api/session/{id}`: если
     `time.idle >= time.busy` (сессия реально свободна) — показать **одно**
     уведомление; иначе ждать следующего события.
3. `permission.asked` / `form.created`: дедуплицировать по `id` запроса,
   уважать `notify`, не спамить.
4. `page.html`: убрать `BR.notify` при `busy → idle` (нативный watcher уже
   уведомляет) либо явно проверять `readSettings().notify`; оставить только
   вибрацию/звук, когда приложение открыто.
5. Проверить: длинный ответ с 3–5 инструментами → **одно** уведомление в
   конце; галочка выключена → ни одного; приложение открыто → без
   уведомления (только вибрация); в фоне → одно.

### Критерий готовности

За один полный ответ приходит ровно одно уведомление «Ответ готов», и только
при включённой галочке.
